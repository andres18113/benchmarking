# Lab 02 — Algorithm Benchmarking: Duplicate Detection

**Course:** Algorithms · Week 2 — Algorithmic efficiency and complexity
**Repository:** `laboratorio-02-eficiencia-complejidad`

## 1. Problem

Given a list of integers, determine whether it contains at least one repeated value.
Two correct strategies that always return the same answer are implemented, instrumented and
measured on exactly the same data:

| | Strategy | Idea | Time | Extra space |
|---|---|---|---|---|
| **A** | Nested loops (pairwise comparison) | Compare every element `data[i]` with every later element `data[j]` (`j > i`). | O(n²) worst case | O(1) |
| **B** | Single pass (hash set) | Walk the list once, remembering seen values in a `set`; stop at the first value already seen. | O(n) worst case (average O(1) per lookup) | O(n) |

Both follow the pseudocode from slide 6 literally, including the `comparisons` counter.

## 2. Hypothesis

* For lists **without** duplicates (and with the only duplicate at the end), A performs
  n(n−1)/2 comparisons and B performs n. When n grows 10×, A's time should grow ≈100× and
  B's ≈10×, so B scales far better and A becomes infeasible for n ≥ 100,000.
* When a duplicate appears **early**, both algorithms stop after 1–2 comparisons, so the
  input distribution, not only n, determines the cost.
* B pays for its speed with O(n) extra memory; A uses O(1).

## 5. Running

```bash
python src/main.py                     # full experiment (≈ 20 s) → results/benchmark_results.xlsx
python -m unittest discover -s tests   # correctness tests
```

The program writes the workbook, re-opens it with openpyxl to verify it, and exits with code 0
only if every coherence check passed.

### Options

| Option | Default | Meaning |
|---|---|---|
| `--sizes N ...` | `100 1000 10000 100000 1000000` | Input sizes |
| `--scenarios S ...` | all four | `random_unique`, `random_with_duplicates`, `early_duplicate`, `late_duplicate` |
| `--repetitions R` | `3` | Timed repetitions per measurement (minimum 3) |
| `--seed S` | `2026` | Base seed for the datasets |
| `--max-comparisons-a C` | `100000000` | Skip Algorithm A on datasets that need more than C comparisons |
| `--no-limit` | off | Run Algorithm A on everything, however long it takes |
| `--no-edge-cases` | off | Skip the edge cases |
| `--output-dir DIR` | `results/` | Where to write the results |
| `--excel-name NAME` | `benchmark_results.xlsx` | Workbook name |

### Large tests (voluntary)

Algorithm A is quadratic. Before running A, the program computes **exactly** how many comparisons
it will need (closed-form formula, verified against the instrumented counter in every run and in
the tests). If that number exceeds `--max-comparisons-a`, the run is **not executed** and is
recorded in the *Skipped Tests* sheet with the reason and the command to run it. No time or
operation count is invented for skipped runs: their cells say `SKIPPED`.

```bash
# A at n = 100,000 without duplicates: 4,999,950,000 comparisons, ~3 min per repetition here
python src/main.py --sizes 100000 --scenarios random_unique --max-comparisons-a 5000000000 \
       --no-edge-cases --output-dir results/voluntary_n100000

# Everything, no limit (A at n = 1,000,000 without duplicates would take hours per repetition)
python src/main.py --no-limit
```
